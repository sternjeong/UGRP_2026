작성 2026-08-03 · 관련: PROJECT_DESIGN.md §7 축D

1

온톨로지란 무엇인가

일상적으로 "온톨로지"라는 말은 종종 "잘 정리된 태그 체계" 정도로 오해되지만, 형식 온톨로지(formal ontology)는 그보다 훨씬 강한 것이다. 태그는 사람이 읽고 판단하는 라벨이지만, 온톨로지는 기계가 논리적으로 추론할 수 있는 명제들의 집합이다.

정의 — 형식 온톨로지

어떤 도메인(예: "포스텍의 교과목과 연구실")에 존재하는 개념(Class)·개체(Individual)·관계(Property)를, 컴퓨터가 모순 없이 자동으로 추론할 수 있는 형식 논리 언어(대개 OWL)로 기술한 것.

태그 체계와 형식 온톨로지의 차이는 "관계에 대해 뭘 할 수 있는가"에서 갈린다.

Flat 태그형식 온톨로지
"A는 B다" 표현가능 (라벨 부착)가능
"A가 B면 자동으로 C다" 추론불가능 — 사람이 매번 확인가능 — reasoner가 자동 도출
모순 자동 검출불가능가능 — "A이면서 not-A"를 reasoner가 잡아냄
깊이 무관 탐색수동 순회 필요공리 하나로 자동 전파

3분커리에서 "LLM beam search는 추론 깊이가 얕지만, 우리 온톨로지는 깊이 무관하게 논리적으로 완전한 다단계 추론이 가능하다"고 어필하려는 이유가 바로 이 표의 마지막 두 줄이다 — 태그로는 절대 못 하고, 온톨로지로는 공짜로 되는 일이기 때문이다.

2

Description Logic의 기본 어휘

OWL은 Description Logic(DL, 기술논리)이라는 논리 체계 위에 세워져 있다. DL의 어휘 세 가지만 알면 우리 스키마를 전부 읽을 수 있다.

Class (개념)

개체들의 집합. 예: Course, Lab, ResearchTopic. 사람이 흔히 말하는 "타입"이나 "카테고리"에 해당한다.

Individual (개체)

실제 데이터 한 건. 예: EECE233이라는 개체는 Course 클래스의 인스턴스다.

Object Property (관계)

개체와 개체를 잇는 이항 관계. 예: hasPrerequisite(EECE233, MATH110). 관계 자체에도 성질(property characteristics)을 선언할 수 있다는 게 태그 체계와의 결정적 차이다 — 3장에서 자세히 다룬다.

예시 — 우리 스키마를 DL 어휘로 읽기
Class: Course, Lab, Professor, ResearchTopic, Skill, Department
Individual: EECE233 (a Course), 통신시스템연구실 (a Lab)
ObjectProperty: hasPrerequisite, isSubfieldOf, coversTopic, requiresSkill, hasSynergyWith
3

OWL 2 DL과 결정가능성

OWL 2에는 표현력이 다른 여러 프로파일(EL, QL, RL, Full, DL)이 있다. 우리가 쓰는 OWL 2 DL은 "표현력과 계산 가능성 사이의 최적 지점"으로 설계된 버전이다.

정의 — 결정가능성(decidability)

어떤 질문(예: "이 온톨로지에 모순이 있는가?")에 대해 유한 시간 안에 반드시 답이 나옴이 수학적으로 보장되는 성질. OWL Full은 표현력은 가장 크지만 결정 불가능한 질문이 생길 수 있어 reasoner가 무한루프에 빠질 수 있다. OWL 2 DL은 표현력을 일부 제한하는 대신 이 보장을 얻는다.

실무적으로 이게 중요한 이유: reasoner(4장)가 "일관성이 있다/없다"를 항상 유한 시간에 답할 수 있어야 파이프라인에 자동으로 넣을 수 있다. OWL Full로 갔다면 이 보장이 없어 "reasoner가 멈추지 않을 수도 있다"는 리스크를 안게 된다.

4

HermiT·Pellet 같은 reasoner는 온톨로지를 "실행"하는 엔진이다. 세 가지 표준 추론 서비스를 제공한다.

5

관계의 성질 — transitive와 property chain

DL에서 관계(Object Property)는 그냥 화살표가 아니라, 스스로 성질(characteristic)을 가질 수 있다. 우리 스키마에서 실제로 쓰는 두 가지만 짚는다.

Transitive (전이성)

정의

관계 R이 transitive면: R(A,B) ∧ R(B,C) → R(A,C)가 항상 성립한다.

hasPrerequisite와 isSubfieldOf가 이 성질을 갖는다. "A가 B의 선수과목, B가 C의 선수과목이면 A는 C의 선수과목이기도 하다"는 게 자동으로 참이 된다 — 매 쌍을 일일이 다 적을 필요가 없다.

  • ElectricalEngineering
    • Communications
      • InformationTheory
        • SemanticCommunication
          • JointSourceChannelCoding

depth 5의 isSubfieldOf 체인. transitive 덕분에 "JointSourceChannelCoding은 ElectricalEngineering의 하위분야다"를 명시적으로 적지 않아도 reasoner가 도출한다 (CQ7).

Property Chain (관계 합성)

정의

서로 다른 두 관계를 이어붙여 세 번째 관계를 자동 생성하는 공리. R1 ∘ R2 ⊑ R3: "R1으로 갔다가 R2로 가면, R3로 간 것과 같다."

우리 스키마에서 CQ7("깊은 노드와 관련된 모든 Course/Lab을 depth 무관하게 찾기")을 실제로 구현하는 공리가 바로 이것이다:

SubObjectPropertyOf(
  ObjectPropertyChain(coversTopic isSubfieldOf)
  coversTopic
)
Lab --coversTopic→ SemanticCommunication --isSubfieldOf→ Communications ⟹ Lab coversTopic Communications

리프 노드(SemanticCommunication)에만 coversTopic 엣지를 심어두면, 상위 노드(Communications)로의 전파는 사람이 손댈 필요 없이 reasoner가 이 공리 하나로 전부 처리한다.

주의

hasSynergyWith는 의도적으로 non-transitive다. "A가 B에 시너지, B가 C에 시너지"라고 "A가 C에도 시너지"가 자동으로 참이 되게 두면, 관계가 없는 과목 쌍까지 실수로 강하게 연결돼버린다. 이건 §7.2에서 hasPrerequisite와 hasSynergyWith를 분리한 것과 같은 이유의 설계 판단이다.

6

Competency Questions 방법론

온톨로지를 "일단 클래스부터 그리면서" 시작하면 대개 실패한다. 표준 절차는 반대 방향이다 — "이 온톨로지가 답해야 하는 질문들"을 먼저 자연어로 나열하고, 그 질문들을 답하는 데 필요한 최소한의 클래스·관계·공리만 역산해서 스키마를 만든다.

정의 — Competency Question(CQ)

온톨로지가 반드시 답할 수 있어야 하는 자연어 질문. 스키마 설계의 요구사항 명세서 역할을 한다.

절차는 4단계다:

  1. CQ 정의 — "학생이 목표 과목까지 최소 선수과목 체인은?" 같은 질문들을 도메인 전문가(팀)가 직접 작성
  2. 개념화 — 각 CQ를 답하는 데 필요한 Class/Property/Axiom을 역산
  3. OWL 형식화 — Protégé 등으로 실제 논리 언어로 작성
  4. Reasoner 검증 — 일관성 검사 + 실제로 CQ에 답이 나오는지 SPARQL 등으로 확인
우리 프로젝트에서는

3분커리는 이미 9개 CQ를 정의했고(7장 표), 그중 CQ2(경로계획 제약 — 축C 스트레치 목표라 스코프 밖)는 제외하기로 했다. 스키마의 모든 클래스·관계는 "이 CQ를 풀기 위해 필요한가?"라는 질문 하나로 정당화된다 — 필요 없는데 "있으면 좋을 것 같아서" 넣은 요소는 없어야 한다.

8

LLM-assisted, reasoner-gated 워크플로우

Gemini/Claude로 온톨로지 구축을 돕는다는 계획과, 축D가 근접 선행연구(Abu-Rasheed et al., 2025)와 차별화하려는 지점 — "LLM이 그래프 완성을 직접 담당해 노이즈/비일관성이 있는" 접근 — 은 자칫 충돌한다. 이를 가르는 원칙 하나:

원칙

LLM은 제안(propose)만 하고, reasoner의 일관성 검증을 통과한 것만 커밋(commit)된다. LLM 출력이 그 자체로 최종 사실이 되는 지점은 없다.

단계별로 LLM의 역할과 리스크 수준이 다르다.

단계LLM 활용리스크안전장치
ResearchTopic 계층 초안후보 트리 제안낮음팀이 Protégé에서 직접 검토·확정
앵커문장 작성노드별 대표 문장 초안낮음팀 검수, 구조에 영향 없음
coversTopic 인스턴스보조 신호로만 (메인은 임베딩 유사도)중간임베딩 결과와 불일치 시만 사람 검토
OWL 공리 문법 생성이미 확정된 논리를 문법으로 번역낮음공리 자체는 사람이 확정, LLM은 번역만
모든 삽입 후——reasoner 일관성 검사 필수 통과, 실패 시 반려
우리 프로젝트에서는

"LLM 그래프 완성 vs reasoner 검증된 그래프"라는 §7 축D의 차별화 문구는, LLM을 안 쓴다는 뜻이 아니라 LLM 출력이 절대 검증 없이 그래프에 커밋되지 않는다는 뜻으로 해석해야 한다. 이 원칙이 지켜지는 한 LLM 활용과 방법론적 차별화는 모순되지 않는다.

이 챕터의 "LLM"은 축A/축E와 다른 세 번째 용도다

축A(BGE-m3)는 서비스 운영 중 실시간으로 도는 임베딩 인코더, 축E(경량 로컬 LLM)는 서비스 운영 중 학생에게 추천 근거를 설명하는 생성 모델이다. 반면 이 챕터의 Gemini/Claude는 개발 단계에서 팀이 온톨로지를 저작할 때만 쓰는 도구이며, 산출물(OWL 파일)만 남고 서비스가 실제로 돌아갈 때는 관여하지 않는다.

9

실습 도구 — Protégé와 owlready2

Protégé

온톨로지 저작을 위한 표준 GUI 도구. 클래스/관계/개체를 마우스로 만들고, HermiT·Pellet reasoner를 메뉴에서 바로 실행해 일관성을 확인할 수 있다. 소규모 스키마 설계·검토 단계(6~7장)에 적합하다.

owlready2

용어 정리

Class (Concept)
개체들의 집합. 예: Course, Lab.
Individual
클래스의 실제 인스턴스 한 건. 예: EECE233.
Object Property
개체 간 이항 관계. 예: hasPrerequisite.
Axiom
온톨로지에 참이라고 선언하는 논리 문장. 클래스 정의, 관계 성질, property chain 모두 axiom이다.
Transitive Property
R(A,B) ∧ R(B,C) → R(A,C)가 항상 성립하는 관계.
Property Chain
두 관계를 합성해 세 번째 관계를 자동 생성하는 공리.
Reasoner
온톨로지의 일관성 검사·분류·함의 추론을 수행하는 엔진. 예: HermiT, Pellet.
Consistency Checking
온톨로지에 논리적 모순이 있는지 확인하는 reasoner의 기본 서비스.
Competency Question (CQ)
온톨로지가 반드시 답할 수 있어야 하는 자연어 질문. 스키마 설계의 출발점.

표현력과 결정가능성 사이의 균형을 맞춘 OWL 2의 표준 프로파일.
